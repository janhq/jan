# Login UX Extension Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `/login` a direct five-provider sign-in picker and make `/model` a full-screen provider-scoped model browser that exposes models discovered by account login immediately.

**Architecture:** Keep OAuth, PKCE, callback validation, token exchange, model discovery, and persistence in `src-tauri/src/core/cli/auth/account.rs`. Keep provider capability metadata in the typed auth catalog. Keep TUI interaction state in `src-tauri/src/core/cli/tui.rs`: direct provider routing, an opaque OAuth prompt that never renders codes or state, and a separate model-hub state machine that consumes the existing reachable `(provider, model)` list.

**Tech Stack:** Rust 2021, Tokio, Ratatui 0.30, Crossterm, Reqwest, existing Jan credential/config stores, embedded Rust unit tests.

## Global Constraints

- Preserve the five-provider catalog order: Codex, Claude, OpenCode, DeepSeek, Tokamak.
- Codex and Claude use the existing PKCE browser flow; OpenCode, DeepSeek, and Tokamak use API-key login.
- Do not render API keys, authorization codes, OAuth state, PKCE verifiers, access tokens, or raw persistence errors.
- Do not perform network I/O in the Ratatui render loop.
- Cancelled or stale account-login tasks must not emit success or failure notes.
- `/model` lists only reachable configured provider models and preserves the raw model id passed to the runtime.
- Role assignment, role-management UI, desktop login, credential-store migration, and new providers are out of scope.
- Use existing dependencies and existing test modules; do not add a generic authentication framework.

- [ ] **Step 3: Implement manual input parsing without weakening browser callback validation**

Keep `parse_callback` strict: it must continue requiring a URL, a state, a matching expected state, and a non-empty `code`. Add `parse_manual_callback` with this order:

1. Trim input and reject empty input.
2. If the input parses as a URL, extract `code` and optional `state`; reject a supplied state that differs from `expected_state`; require a non-empty code.
3. If the input starts with `code=` or `?code=`, parse it as query parameters with the same optional-state check.
4. Otherwise split once on `#`; treat the left side as a raw code and the right side, when present, as the optional state. A raw code without a state is accepted because PKCE still binds the code to this login attempt.
5. Reject an empty code and return only safe, user-actionable messages.

- [ ] **Step 5: Add the callback/manual race**

Implement `complete_callback_login_with_manual` with a pinned callback future and a loop over manual messages:

```rust
pub async fn complete_callback_login_with_manual(
    listener: tokio::net::TcpListener,
    login: AccountLogin,
    mut manual: tokio::sync::mpsc::UnboundedReceiver<String>,
) -> Result<AccountProvider, String> {
    let callback = accept_callback(listener, &login);
    tokio::pin!(callback);
    let code = loop {
        match manual.try_recv() {
            Ok(input) => {
                if let Ok(code) = parse_manual_callback(&input, &login.state) {
                    break code;
                }
            }
            Err(tokio::sync::mpsc::error::TryRecvError::Empty) => {}
            Err(tokio::sync::mpsc::error::TryRecvError::Disconnected) => {
                break callback.await?;
            }
        }
        tokio::select! {
            result = &mut callback => break result?,
            input = manual.recv() => match input {
                Some(input) => {
                    if let Ok(code) = parse_manual_callback(&input, &login.state) {
                        break code;
                    }
                }
                None => break callback.await?,
            },
        }
    };
    complete_code_login(login, code).await
}
```

The actual implementation may use `AccountLogin::parse_manual_input`, but it must retain the callback future while invalid manual messages are ignored. The TUI will validate first to display the safe parser error; the account task validates again before exchanging.
